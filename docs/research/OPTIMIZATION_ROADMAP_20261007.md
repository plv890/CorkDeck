## 1. Начать с реальных очередей, а не с назначения игры одному ядру

В `references/mesa-switch/src/util/u_queue.c` Horizon workers явно получают
mask=0x6: только ядра 1 и 2, preferred core чередуется. В
`src/util/disk_cache.c` очередь `disk$` создаётся с лимитом четырёх workers.
Linux-вариант понижает их приоритет через nice, но этот участок не применяется
на Horizon. Фактический приоритет HOS зависит от создания потока и должен
измеряться. Это отдельная политика от Wine/DXVK имён, распознаваемых Autorun.

Предлагаемый интерфейс: Mesa сообщает runtime роль очереди, а runtime задаёт
разрешённую маску, preferred core и приоритет. Не менять маску всех очередей
одним глобальным флагом: graphics submit и дисковая запись имеют разные задачи.

Первые кандидаты: cache writer на core 3 с низким приоритетом; compiler workers
с preferred core 3 и доступом к свободным application cores; графический submit
отдельно. Сохранить явно заданную игрой affinity. Сравнить одну/две/три compiler
workers при неизменных clocks и cache. Предпочтительное ядро не означает
фактическое постоянное исполнение на нём.

[DXVK developer guidelines](https://github.com/doitsujin/dxvk/wiki/Developer-guidelines)
подтверждают использование собственных workers для тяжёлой части компиляции.
[Обсуждение #3235](https://github.com/doitsujin/dxvk/issues/3235) содержит
пользовательский пример конкуренции фоновой компиляции с игрой, но относится
к DXVK 2.1 на другом железе и не является доказательством выигрыша на Switch.

## 2. RAM как верхний уровень кэша

Первый вариант — ограниченный LRU горячих shader-cache записей, например
16–32 MB как начальный измеряемый бюджет, с уменьшением при нехватке heap.
Чтение: RAM → существующий SD-кэш → компиляция. Новая запись видима из RAM
сразу, сохранение в SD идёт через фоновую очередь с ограниченным backlog.
Нужны проверка целостности, разделение по версии backend/драйвера и корректная
синхронизация чтения с записью. RAM-размер пока проектный, не результат замера.

Полностью переносить кэш в временный RAM-диск пока хуже: пропадает прогрев
между запусками, а Horizon не даёт Linux tmpfs одной переменной окружения.
Нужен native backend памяти или существующая проверенная memfile-абстракция.
Не применять её к всем save/config файлам.

В конце Dishonored доступно около 615 MB native heap. SD read cache занимал
33 MB из возможных 192 MB. Увеличение общего лимита без измерения промахов
не обосновано. RAM-кэш компилированных шейдеров и кэш чтения игровых ресурсов
— разные места интеграции.

[Документация Mesa](https://docs.mesa3d.org/envvars.html) описывает постоянные
shader caches, hit/miss statistics и Fossilize. У single-file FOZ нет ограничения
через MESA_SHADER_CACHE_MAX_SIZE; наш Switch-порт выбирает single-file по
умолчанию, поэтому эта переменная сама по себе не ограничит его размер.

## 3. FEX: lookup cache сначала, постоянный JIT cache затем

В интерфейсе Autorun уже доступны L2 lookup cache и dynamic L1. Проверить
эффективные значения и размер/промахи прежде, чем увеличивать память. Локальный
`horizon-wine/fex/cache_policy.h` уже задаёт native code-cache limit и размеры
lookup caches для wide host; увеличение этих чисел не гарантирует уменьшения лагов.

[FEX-2609](https://fex-emu.com/FEX-2609/) добавляет экспериментальный постоянный
JIT-кэш FOZ и уменьшает contention при параллельной трансляции. Эти JIT changes
уже входят в используемую версию, повторно переносить их не требуется.

DiskCache нужно отдельно адаптировать к нашему Wine/Horizon bridge. Upstream
пока предупреждает о неограниченном росте и неполной инвалидизации. Кроме того,
наш `horizon.patch` отключает PermissionSMC при DISKCACHE/ENABLECODECACHINGWIP:
кэшированные трансляции не сохраняют сведения о возможности trap страниц.
Поэтому простое FEX_DISKCACHE=1 нельзя объявить безопасной готовой оптимизацией.
Нужны корректная SMC-инвалидизация, версия/идентичность игровых модулей и
ограниченный размер. TSO остаётся включённым.

## 4. DXVK и frame pacing

Уже есть три compiler workers и обычный upstream DXVK 3.1.1. Старый DXVK_ASYNC
не добавляет async-патч этой DLL. Оценивать конкретные сборки и подтверждённые
возможности драйвера, а не переносить рекомендации для RADV/Steam Deck.

Подготовлен `../artifacts/clock-language-20261007/dxvk-candidate.conf`:
GPL=True и фиксированные три compiler workers. В этой версии True сохраняет
GPL и подавляет background optimized-pipeline compilation. Цена может быть
в памяти и эффективности GPU. Сравнение делать отдельно от core policy.
VSync/frame limit оценивать по распределению времени кадра после компиляции.

## Как принимать изменения

Цель — уменьшение редких длинных кадров и повторной работы, затем средний FPS.
Один и тот же сценарий, одинаковые частоты/сборки, одна переменная за сравнение.
Тёплый и холодный cache оценивать отдельно. Отдельно измерять RAM, SD I/O,
суммарное время и CPU-time потока; ожидание работы другого потока не считать
временем собственной компиляции. Зависания остаются отдельным критерием:
ускорение, которое ломает длительный запуск, не становится значением по умолчанию.
