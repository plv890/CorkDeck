## Вывод

Autorun уже имеет разрешение использовать CPU core 0–3. Первый кандидат —
согласовать политики потоков Wine, DXVK и native Mesa. Оснований начинать
с изменения планировщика Mesosphere сейчас нет. Core 3 доступен совместно
с системными потоками; это не четвёртое эксклюзивное ядро приложения.

## Три разных ограничения

1. **Права процесса.** Обычный upstream nx-hbloader объявляет core 0–2.
   Наш forwarder объявляет 0–3, priority 28–63 (kernel flags 0x030073f7).
   GTA addon NPDM объявляет 0–3, priority 28–59 (0x030073b7).
   Loader проверяет запрашиваемые диапазоны относительно ACID. Изменение
   метаданных отдельного запуска отличается от глобального изменения ядра.
2. **Affinity конкретного потока.** Доступ процесса к четырём ядрам не отменяет
   маску 0x6 или singleton 0x2, установленную библиотекой. Нужны реальные
   эффективные маски и коды возврата svcSetThreadCoreMask.
3. **Готовая к исполнению работа.** Поток, ожидающий lock, GPU или I/O, не
   ускорится только от расширения маски. Один последовательный поток игры
   нельзя выполнять одновременно на нескольких ядрах сменой affinity.

## Что уже делает ядро

Проверен исходный код Atmosphere **1.11.2**, соответствующий установленной
версии. KScheduler::UpdateHighestPriorityThreads ищет потоки для свободных
ядер через suggested queues и выполняет миграцию; другие пути yield/rotation
также мигрируют потоки. KThread хранит affinity отдельно от ideal/active core
и уведомляет scheduler при её изменении. Поэтому preferred core — подсказка,
а разрешённая маска определяет возможность миграции.

HighestCoreMigrationAllowedPriority = 2. Это специальная граница системных
приоритетов в отдельных путях миграции, а не запрет миграции обычных потоков
Autorun с приоритетами 28–63. Меньшее число означает более высокий приоритет.
Высокоприоритетная системная работа по-прежнему может занимать core 3.

## Подтверждённые ограничения нашей сборки

| Место | Текущее поведение | Кандидат исследования |
|---|---|---|
| Mesa util_queue, u_queue.c:275 | Все такие workers получают mask 0x6, preferred 1/2 | Политика по роли очереди, доступ к core 3 |
| Mesa disk_cache.c:94 | До четырёх disk$ workers; Linux nice не действует на Horizon | Один/два writers с пониженным HOS priority и ограниченным backlog |
| Wine horizon_pin_current_thread | При широкой автоматической маске preferred = младший разрешённый core, обычно 0 | Распределённые preferred hints при широкой маске |
| Runtime wine_nx_thread_balance | В обычной политике process_mask &= 7, перемещение через singleton affinity | Сравнить kernel migration и роль-aware balancing |
| Runtime policy 3 | Широкая маска разрешена, custom balancing выключен | Не охватывает жёсткую native маску Mesa 0x6 |
| Server connection | Следует affinity своего Wine клиента | Измерить конкуренцию client/server перед разделением |

Wine/FEX выполняют часть Windows API и трансляцию непосредственно в потоке
игры. Выделить всё Windows-окружение на отдельное ядро таким способом нельзя.
Отдельно размещать можно действительно независимые workers и server work.

## Предлагаемые варианты

**A — миграция средствами Horizon.** Автоматические игровые потоки и graphics
submit имеют широкую разрешённую маску 0xF, обычные приоритеты и распределённые
preferred hints. Явную affinity игры сохраняем. Фоновые compiler/cache workers
получают preferred 3, широкую маску и проверяемый пониженный приоритет.

**B — разгрузка основных потоков.** Игровые потоки преимущественно 0–2;
независимая фоновая работа предпочитает 3 с возможностью использовать другие
свободные ядра. Это размещение ролей, а не закрепление всех compiler workers
на одном core 3. Жёсткий mask 0x8 сериализует их и может увеличить загрузку.

Для обоих вариантов нужен native hook из Mesa util_queue в runtime с ролью
очереди и проверкой прав. Пересобрать SDK Mesa archives и NRO достаточно;
в исходных данных нет требования патчить firmware. Нельзя глобально обходить
runtime wrapper для любых потоков или переносить критический graphics submit
в низкоприоритетную очередь без отдельного сравнения.

## Что должно решить эксперимент

Сначала добавить регистрацию native workers и компактную телеметрию:
роль, effective affinity, priority, CPU delta, очередь и время ожиданий.
Preferred core не считать фактическим residency. Данные top-12 Wine registry
не покрывают весь CPU расход Mesa. Для широких масок нужны отдельные редкие
замеры фактического core во время работы; это выборка, не полная timeline.

Сравнивать A/B с текущей политикой при одинаковых clocks, compiler count,
сцене и состоянии кэша. Сохранять p50/p95/p99 времени кадра, загрузку,
длительность компиляции/загрузки и незавершённые ожидания. Дать медленному
старту 5–10 минут. Новые проверки проводить после отдельного возобновления
игровых тестов пользователем; прежний запрос закончить тесты сохраняется.

К патчу планировщика возвращаться только если готовые потоки с широкими
масками устойчиво ждут CPU при свободных разрешённых ядрах, а существующие
пользовательские ограничения исключены. Одного показания «ядро 100%» мало:
важно, чем оно занято и есть ли независимая готовая работа.

33% — арифметика четырёх полностью свободных ядер вместо трёх, не прогноз
FPS. Здесь core 3 разделяется с ОС, а последовательные участки и синхронизация
остаются. Реалистичная цель — уменьшение конкуренции и пиков времени кадра;
размер выигрыша пока не установлен. Зависания Dishonored требуют отдельного
анализа ожиданий и не объясняются отсутствием четвёртого ядра автоматически.
