## Dishonored

Подтверждены policy 4, shader RAM 32 MB, FEX L2 enabled, два DXVK compiler
workers и GPL=True. Последняя PROGRESS: **606 s, frames=7478**, heap used
2675 MB / free 414 MB. В полученном логе нет явного fatal-сообщения. Это не
доказательство отсутствия всех зависаний: журнал заканчивается до нормального
EXIT, а последнее длительное ожидание отдельного idle worker может быть нормой.

Положительные интервалы aggregate frame counter: медиана **19.05/s**, максимум
**28.91/s**, 40 интервалов. Включены разные сцены и загрузка, нет одинакового
контролируемого маршрута; эти числа нельзя объявлять benchmark FPS или опровергать
субъективные 30+ FPS. Пользователь сообщил меньше фризов/больше стабильности,
при возможно меньшем среднем FPS — его наблюдение сохраняется отдельно.

Hot cache: 418 hits / 14721 misses, **2.76%**, 14721 puts / 14209 evictions,
5423516 bytes (~5.2 MiB) из бюджета 32 MiB. Есть ограничение 512 entries, которое
может срабатывать раньше byte cap; текущий cache не использует весь бюджет.
Увеличение slots без hash index увеличит стоимость линейного поиска. Кандидат
следующей реализации — индексированный LRU с тем же byte cap, измерением hit rate
и lookup latency, а не слепое увеличение общего объёма памяти.

Плавность могла улучшиться от прогрева постоянного SD-кэша, меньшего количества
workers и GPL=True (без background optimized pipelines). По этим логам вклад
каждого изменения не разделён. GPL=True может снизить эффективность GPU.
CPU service reads были 1428–2499 MHz; режим часов также не одинаков во всех
интервалах. Профили разгона не менялись.

## The Forest

Запускалась непосредственно `The Forest/TheForest.exe`, machine=AMD64,
FEX-2609, `no args.txt`. Mono DLL успешно загружена, DXVK 3.1.1 и два compiler
workers инициализировались. Поэтому первоначальное описание «до инициализации
графики» уточняется: **до первого кадра**, графический backend уже работал.

PROGRESS 603 s: **frames=0**, heap used 1358 MB / free 1732 MB. Последние
зарегистрированные потоки использовали 0.00 cores. Hot cache 9 hits/1847 misses.
Отдельное меню настроек не подтверждено причиной. Main thread в последнем
встроенном STALL: server_wait → server_select/call → horizon_pipe_read_r →
condvarWaitTimeout; ряд workers стоит в NtWaitForAlertByThreadId/futex. Это
ожидания, не найденный владелец lock или доказанный Mono GC deadlock.

`TheForest-symbols.txt` расшифрован offline по точному ELF -7. В JSON сохраняется
последняя увиденная строка каждого thread; исчезнувшие threads могут относиться
к более ранней фазе, поэтому нельзя объявлять каждую строку одновременным
финальным snapshot. Тест продолжался более десяти минут без первого кадра.

## Assassin’s Creed

Точный диалог: **Steam Error — Application load error 2:0000065558**.
Перед ним загрузчик пытается найти `Steam.dll` в папке игры, `C:\Steam` и
корне C:, получает STATUS_DLL_NOT_FOUND (c0000135). Это конкретный провал
запуска Steam-окружения, не наблюдаемая GPU/JIT ошибка. Для исправления нужно
проверять штатные launch metadata и подлинные компоненты установленной игры;
подмена DRM/auth DLL или игровые EXE patches не выполнялись.

## GDB: неудачная диагностическая сессия и восстановление

Inventory работал, current Application PID был 141. Первая script-попытка
не выполняла attach: SDK GDB не собран с Python. Следующая попытка plain GDB
attach/stack capture не завершилась, выдавая `Ignoring packet error`.
SIGINT не завершил её; собственный GDB-контейнер остановлен. Последующие
попытки связи не отвечали. Пользователь сначала сообщил HOME работает, затем
исправил: HOME **тоже не работала**, и физически перезагрузил консоль.
Первый вывод об отсутствии общего зависания был преждевременным и отозван.

После перезагрузки связь восстановлена, DBI открыт и логи сохранены. Штатный
system_settings.ini восстановлен byte-for-byte из backup, readback проверен;
отключение GDB происходит при **следующей перезагрузке**. Никаких новых attach
после восстановления не выполнялось. Hardware/system hang после GDB нельзя
использовать как доказательство нестабильности пользовательского разгона или
как обычный игровой benchmark.

Обнаружен конкретный риск конфликта в текущем sys-botbase source:
`getTitleID → getMetaData → attach → svcDebugActiveProcess`. Таким образом,
сам metadata probe не является полностью свободным от debug attach.
`attach()` возвращает void, не обнуляет global debughandle после close/failure,
а `getMetaData()` продолжает чтение без проверки успеха attach. Это кандидат
для исправления общего механизма и разнесения GDB/sys-botbase диагностики;
точная причинная связь с общим hang пока не установлена. Sysmodule binary
в этом этапе не менялся. Новые GDB-тесты требуют исключить конкурирующие
metadata queries, ограничить ожидание и подтвердить detach отдельно.
